Executive summary

An agent that investigates an alert the way the team does, and shows its evidence.

Management asked for AI Ops: an assistant that can trace a problem to its root cause and take on service-management work. The fastest credible path is to build it on SAMI'X, which already holds the one thing every AIOps project spends months assembling: hosts, alerts, capacity, topology, owners and 30 days of history from five tools in one model. The agent gets read-only tools over that data, produces a structured root-cause analysis with evidence, and never acts on production without a person clicking.

What we are building

Three capabilities, delivered in this order. Each one is useful on its own.

1 · Investigate
Root-cause analysis on demand

An Investigate button on any alert. The agent gathers evidence from SAMI'X and returns ranked causes, blast radius, the next step and who to call.

2 · Assist
Service-management work

Incident summaries, escalation mails with the RCA attached, shift handover, post-incident reports, ticket drafts. The paperwork, written from evidence.

3 · Anticipate
Correlation and early warning

Alert storms grouped into one incident, recurring patterns surfaced, capacity that will run out before it does.

The unit of value is an investigation: an operator (or a scheduled trigger) points the agent at a symptom, the agent works the problem with the same sources a senior engineer would open, and hands back a document the engineer can verify line by line. Speed matters, but the reason this will be trusted in a telecom operations room is that every claim carries the evidence it came from.

What "training the agent" means here

Setting the expectation early, because the word suggests something it is not.

We will not train a model. The model already knows how to reason about infrastructure; what it does not know is our estate, our history and our conventions. It learns those four ways:

  1. Tools — access to live SAMI'X data. This is most of the value and it is ready on day one.
  2. Knowledge — our runbooks, KB articles and the way we name things, retrieved into the investigation when relevant.
  3. Memory — every investigation and the team's verdict on it are stored; the next investigation is shown similar past incidents.
  4. Evaluation — a golden set of past incidents with known root causes. We score the agent against it every sprint and report the number.

That fourth item is what turns this from a demo into an engineering project. Without it nobody can say whether the agent got better this week. With it, the manager gets one chart.

Guardrails that do not move

  • Read-only tools only. The agent reaches Zabbix and Dynatrace through the same transports that reject anything but a read. It cannot be prompted into a write because no write exists for it to call.
  • Human in the loop for every action. The agent may propose — a Runbook script, an escalation, a ticket. A person clicks. Nothing on production changes without that click.
  • Evidence or nothing. Every cause in an RCA cites the tool result it came from. A claim without evidence is rendered as a hypothesis, and the card says what could not be checked.
  • Credentials never reach the model. Tool results are built from SAMI'X's own tables; passwords, tokens and SNMP strings are not in them. IP masking is available if policy requires it.
  • Audit log and budget. Every model call and every tool call is recorded with who asked and what it cost. A daily spend cap stops the agent, not the dashboard.
  • Off by default. ENABLE_AIOPS=false ships dark, like Topology and Runbook. Turning it on is a config change, not a deployment.

Model access. The plan assumes the Claude API over HTTPS from the SAMI'X server. The client is one module, so a self-hosted model can replace it later without touching the tools, the UI or the evaluation — but the quality bar in this plan is set with Claude and should be re-measured if that changes. This is decision 1 below.

What an operator gets back. Fixed structure, so it can be verified, exported and compared across sprints.

How it gets better, and how we know

The learning loop and the numbers reported each sprint.

The golden set

Twenty to thirty past incidents where the team knows the root cause — from escalation mails, tickets, WhatsApp threads, memory. For each: the triggering alert, the date, the true cause, what fixed it. This is the "training data" in the only sense that applies. Collecting it is the team's first task and the most valuable thing they will do for this project.

The feedback loop

Every RCA card carries Correct this. The engineer marks the verdict — right, partly right, wrong — and can write the actual cause in a line. That record becomes memory: the next investigation on a similar symptom is shown it. Corrections also feed the golden set, so the evaluation grows from real operations, not from us.

Decisions needed before Sprint 1

Each with a recommendation. Everything below can be changed later; none can be skipped now.

Where the model runs

The Claude API over HTTPS from the SAMI'X server, or a self-hosted model inside the network.

Recommend: Claude API for the pilot. Highest reasoning quality, no infrastructure, and the client is one swappable module. Re-evaluate at the executive demo with the measured accuracy in hand.
What data may leave the network

Investigations send hostnames, alert titles, group names, capacity figures and topology names to the model. Never credentials.

Recommend: allow as-is for the pilot on one service; enable IP masking if policy asks. Confirm with security in writing in Sprint 0.
Ticketing system and API access

ServiceNow, Remedy, Jira or other. With an API, the agent creates draft tickets and reads change records; without, it produces text to paste.

Recommend: request read + create-draft access in Sprint 0; ship Sprint 3 with paste-ready drafts if access is late.
Pilot service

One service with clear ownership, real alert volume and a team willing to review RCAs daily.

Recommend: Billing, or whichever service produced the most escalations in the last 90 days — the alert history can tell us.
Golden-set owner

One senior engineer who signs off on "this was the real cause" for each of the 20 – 30 incidents.

Recommend: Eng. Ahmed Hussien or the on-call lead for the pilot service. Two hours, once.
Monthly spend cap

The agent stops investigating when the cap is reached; the dashboard is unaffected.

Recommend: $300 / month for the pilot — see cost below. Adjust after Sprint 1 with real numbers.
Who may run investigations

Everyone who can open SAMI'X, or only Runbook admins.

Recommend: Runbook admins during the pilot; open it up with phase 2.

What makes this easier than it sounds

  • Build on SAMI'X, do not buy a platform. The data model, the safety transports and the UI exist. The agent is a package and a button.
  • Twenty incidents beat a thousand. A small golden set with confirmed causes is worth more than any volume of unlabeled logs. It comes from the escalation mailbox.
  • Reuse what already works. Runbook sign-in gates the agent. Escalate-to-owner carries the RCA. The Excel template exports it. The service filter defines "the pilot service".
  • One service, three alert types. Narrow scope makes the accuracy number meaningful in two weeks instead of two months.
  • Ships dark. ENABLE_AIOPS off by default; mock mode demos without touching production.
  • Fifteen minutes a week with the manager. Same chart every time: accuracy by sprint. Progress that does not need explaining.
  • Promise diagnosis, not magic. Faster, evidence-backed root cause is a claim we can prove by December. Auto-healing is not, yet.
