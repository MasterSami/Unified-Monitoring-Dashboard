04 · SOURCES & UNIFIED DATA MODEL

Five sources.
One consistent data model.

Each platform contributes what it is genuinely good at. Everything lands in the same Host / Alert / Capacity / Topology schema, so a view written once works for every source — including the ones added later.

01 / INFRASTRUCTURE
Zabbix
Hosts, availability, alerts, per-partition capacity and proxy fleet. Multiple instances supported side by side.
02 / APPLICATION
Dynatrace
OneAgent hosts, services, problems, process ownership and restart-required detection.
03 / NETWORK
NNMi
Network devices, incidents and Layer-2 topology feeding the topology graph and table.
04 / LEGACY INFRA
SiteScope
Hosts and operational events delivered through a controlled, read-only forwarder on the SiteScope server.
05 / ASSET INVENTORY
DV
DigitalView
Huawei asset inventory imported from the vendor export — virtual machines, physical servers, racks and storage.
MODEL  hosts · alerts · capacity · collector_runs · topology_nodes · topology_edges
KEY  UNIQUE(source_platform, source_instance, external_id) → idempotent, no duplicates
SEVERITY  normalized for totals, native label always preserved
DigitalView is an inventory source, not a live monitor. Its hosts are labelled as inventory and are deliberately excluded from availability figures — the dashboard never inflates an uptime number with data nothing is actually watching.

05 · THE OPERATIONAL EXPERIENCE

One dashboard.
Every operational signal.

Seven views plus an always-on source-health strip — one navigation, one login. Each view filters by platform and by instance, refreshes itself in place, and exports to the standard Telecom Egypt Excel template.

▦
Overview Executive KPIs: active servers de-duplicated across tools, critical alerts only, and per-platform host health. Written for management reading, not for engineers.
▤
Capacity CPU, memory and disk per server — and per partition, which is where disk problems actually live. Sorted by pressure, exportable.
⇄
Shared Hosts seen by more than one platform, ranked by coverage. Shows where monitoring overlaps and where it does not.
◈
Alerts Every source in one stream with native severity kept intact, full-text search, and one-click escalation to the resolved owner.
⬡
Agents Agent and host inventory across all sources, with drill-down into a single host and the alerts currently open against it.
◉
Topology Network and service relationships as a table by default and as a graph on demand — and it can be switched off entirely per deployment.
▷
Runbook The admin team's script library behind its own sign-in: pick a script, read exactly what it does, run it, export the result.
◎
Sources Health Always visible in the sidebar: last successful run, failure reason and freshness for every collector, so a silent source is never mistaken for calm.

06 · ACTION, AUTOMATION & REPORTING

Seeing the problem is half.
These close the other half.

The capabilities below are what separate SAMI'X from a read-only console. They were built from the team's own daily work, not from a feature list.

→
One-click escalate to owner From any alert, the owner is resolved out of Zabbix inventory and Dynatrace ownership metadata, and a pre-filled mail opens in Outlook with the host, the alert and the timestamps already written. Manual owner lookup disappears.
▷
Runbook — the team's script library Behind its own username and password. Nine read-only reports run from the browser with no shell, no Python and no copy of the credentials; every one documents its steps, its columns and the API calls it makes. Knowledge stops living on one laptop.
▣
Branded Excel reporting Every view and every Runbook result exports in the standard Telecom Egypt template, carrying the filters that produced it and crediting the script author. Cross-tool duplicates are excluded, with Zabbix as primary. Reports become repeatable.
✉
Server-side mail verification The test mail is sent by the Zabbix server itself, not from the engineer's machine — so it proves the real alerting path works, even when the engineer is on VPN from home. Tests the path that matters.
↻
Processes requiring restart A Dynatrace report listing every process still waiting on a restart after patching, each with its resolved owner, searchable by host name. Turns a patch-window guess into a list.
⚙
Operable by configuration Topology, Runbook, export, mail mode, refresh intervals and page sizes are all environment settings. Features are switched on per deployment without touching code. One build, many environments.
Scripts that change configuration — bulk host creation, user creation, bulk disable — are catalogued and fully documented but deliberately have no Run button. Bulk-disabling monitoring from a dashboard is the kind of mistake discovered a week later; those stay on the command line, where the target list is explicit and reviewable.
