01 · The Problem

Two very different headaches, same root cause

A monitoring tool that only shows what's happening right now is doing half the job. It doesn't warn you before a disk runs out, and it doesn't tell you that the twelve alerts on your screen are actually one problem.

Capacity sneaks up on you

A disk fills slowly for weeks, nobody's watching the trend line, and it becomes an emergency the moment it crosses 100%.

One incident, ten alerts

A database goes down and every service that talks to it starts screaming too. The engineer on call now has ten tickets instead of one story.

Both problems have the same fix in common: stop reacting to individual data points, and start reading them as a pattern.

02 · Capacity Forecasting

A straight line through history — nothing fancier

Every server's disk and memory usage is sampled regularly and kept as history. Once a day's worth of samples is collapsed into a single average point, we fit the simplest line that explains the trend, using ordinary least squares — the same method taught in a first statistics course, not a trained model.

  • Fitted per volume, per host, over a rolling window of recent history
  • CPU is tracked but never forecast — it bounces around a workload, it doesn't accumulate toward "full"
  • The result is a slope in %/day, and a date: when does this line cross the danger zone

03 · Capacity Forecasting

The hard part isn't the math — it's knowing when to stay quiet

A wrong forecast is worse than no forecast, because someone will act on it. Most of the engineering here went into recognizing the cases where a straight line would lie.

Not enough history

Too few points or too short a span, and the answer is "not yet" instead of a fabricated date.

The disk got resized

A volume grown from 100 GB to 500 GB looks like a cliff. Only the samples since the resize are used.

The trend is scattered

Low statistical fit keeps the slope as a hint but drops the date — a confident number from noisy data is the one output that actively misleads.

Already almost full

Dividing by a fraction of a percent produces a date that swings wildly between polls. Under half a point of headroom, the honest answer is simply "now."

04 · Capacity Forecasting

Four bands, one question: how many days do we actually have?

Every fitted series lands in one of four buckets, so the Capacity view can be scanned in seconds instead of read row by row.

A volume already sitting above the 90% line is always Critical, even if it stopped growing — a full disk is a present-tense problem, not a forecast.

06 · Incident Correlation

One root cause. Ten alerts. Ten pages.

Zabbix, Dynatrace and NNMi each raise their own alert the moment something looks wrong to them — with no idea that three other tools just did the exact same thing for the exact same reason. The engineer on call has to manually piece the story back together, usually at the worst possible time.

  • A database host goes down → every dependent service alerts within seconds
  • A single distributed request fails → every hop it touched raises its own alert
  • Nobody wants ten pings for one problem — but nobody wants a missed alert either

08 · Incident Correlation

Why two alerts get treated as one story

Every rule is a plain, checkable statement — never a learned weight nobody can explain in a review.

Same trace

Both alerts came from the same distributed request as it hopped through several services — a Dynatrace trace ID ties them together directly.

Known dependency

The topology map already says one entity calls the other. A problem on the callee is a very plausible reason the caller is unhappy too.

Same entity

CPU, memory and disk alerts all firing on the same host at once are one host having a bad day, not three separate incidents.

09 · Incident Correlation

Who actually started it — a graph question, not a guess

Once an incident's members are known, we ask a very concrete question of the topology: inside this specific group, is there any member that nothing else here is downstream of? That member is a root-cause candidate.

  • No scoring model, no confidence percentage pulled out of thin air
  • When two origins are genuinely tied — no dependency edge between them — both come back as candidates, plainly labeled as a tie
  • Every candidate carries its own evidence: earliest onset, which entities depend on it, what the correlation actually matched on
The house rule behind this whole design: never fabricate certainty. If the data doesn't distinguish between two causes, the incident says so instead of picking one to look decisive.

10 · Under The Hood

Built to survive a Monday morning, not just a demo

The first version worked on a handful of test alerts and then struggled once real traffic hit it. This round focused specifically on making it hold up at real scale.

Where it stood

  • Collector held the database lock across slow network calls
  • Correlation re-picked the same 200 events every run
  • Fresh installs sat with an empty Incidents tab

Where it stands now

  • Network calls run free; only the final write is ever locked
  • Every open event gets its turn, oldest-unreviewed first
  • Default rules seed themselves — Incidents populate on first boot
A correlation batch of 65,000 candidate pairs dropped from 66 seconds to 5.5 — caching each batch's lookups instead of repeating them per pair.
